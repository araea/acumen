# 视频解析

视频站链接不走截图：抖音那类本来就只有登录墙，B 站这类要等播放器起画面，截图慢且信息少。这些链接由「视频解析」插件接，一步到底：**链接进来，片子出去**。

## 一步：就地取片

群里出现一条能解析的视频链接，插件直接取原片发进群——不先回预览，不等引用，也没有要用户记住的指令。触发面是消息里「点开它会去哪」的那个地址，三种形态都算：

1. 正文里的链接；
2. QQ 的小程序卡——地址在 `json` 载荷的 `qqdocurl` 里，正文是空的；
3. 分享卡——地址在 `meta.news.jumpUrl`。

取片：按 `max_size_mb` 挑一档放得下的画质、下载到 `data/video_parse/` 下的临时文件、上传给实现端、按 `send` 配的发法发出去（默认只发视频气泡），最后把本地那份删掉。

成品引用用户贴的那条消息：群里同时有好几条链接时，能看出这个片子是哪一条换来的。**成品自己就是那条消息**，不另发一条正文——正文只有片名、画质、体积这类关于它自己的说明，而群里等的是片子。

说出口的话只有两句，且都只在必要时出现：

- 取片超过 `ack_after_seconds`（默认 20 秒）还没完，回一句 `⏳ 正在取片…`；配 0 就什么都不说。
- 没取到，回一句 `❌ 没取到：<原因>`。原因来自 B 站或下载环节，都是能看懂的一句话（`这条稿件不存在或已被删除`、`被 B 站限流了，过一会儿再试`、`视频超过大小上限`）。

同时最多取两片（`TAKE_GATE`），排队的时间计入那句 ⏳；等闸门不算进单片的下载预算。取片名额在**开始**时占，同一条链接被两条事件同时带进来时只下一遍。

**同一个人**在同一个会话里十分钟内重贴同一条稿件不会下第二遍（`state::claim`）——手滑发两遍、编辑一下再发都落在这个窗口里。换个人贴、隔久了再贴照旧取。没取到会把名额放回去，他重贴一次就能再来。记录落在 `data/video_parse/state.json`，只留一天（判定窗口是十分钟，留一天是为了跨重启也不重复取）。

## 链接准入

`is_video_link` 是唯一的判据，`webshot` 也读它：同一条链接不会既取一遍片又被截一张图。认的是 B 站的**稿件页**（`/video/BV…`、`/video/av…`，含 `m.` 与 `/s/` 前缀）与分享短链（`b23.tv`、`bili2233.cn`）。番剧、直播、空间、专栏、动态页仍归截图。

链接不一定写在正文里。QQ 的小程序卡与分享卡都是整段 JSON，整段落在消息的 `<json>`
元素里，而且载荷里的斜杠常被转义成 `\/`，在字符串上找不到 `https://`。
`command::card_target_url` 按 JSON 解析这段载荷取「点开这张卡会去哪」的地址：
`qqdocurl`（小程序真正打开的页面）优先于 `jumpUrl`（分享卡的落地地址），
`icon` / `preview` 那些图片地址不取。`command::message_links` 把卡片里的地址排在
正文前面一起交给插件，插件取第一个认得的稿件页——所以一个群里贴链接和发卡片
都会取片。

## B 站的几个接口事实

- 稿件信息走 `x/web-interface/view`，取流走 `x/player/playurl`。
- 请求参数用 `fnval=1`（要 mp4 的 `durl`，不要 DASH）：一个文件、不用合流，
  每一段的字节数还写在回包里，所以挑画质之前就能算准体积。
- **UA 必须是桌面浏览器**。分片地址里带着 `platform=pc`，CDN 会按 UA 复核，
  手机 UA 一律 403（实测同一个地址，`Mozilla/5.0` 拿 200、Chrome/Android 拿 403）。
- `Referer: https://www.bilibili.com` 同样必需，缺了分片回 403。
- 未登录时只放 360P/480P，多数稿件给到 720P。要 1080P 及以上得在 `cookie` 里填
  登录态。接口回 `-352` 是风控拦下，也是这一栏能救的。
- 老稿件的 `durl` 会切成好几段，顺序拼进同一个文件即可（它们本来就是同一路 mp4
  的连续分片）。

稿件信息只取取片要用的那几样：稿件号、选中那一 P 的 `cid`、分 P 号、总 P 数、
标题（当文件名）。封面、播放量、UP 主都不取——那是给预览用的，现在没有预览。

## 配置

见 `config.example.toml` 的 `[video_parse]`：`max_size_mb`（默认 80）、
`prefer_quality`（默认 64）、`send`（默认 `bubble`，与 `[oai] video_send` 同一套写法）、
`timeout_seconds`、`ack_after_seconds`（默认 20 秒）、`cookie` 与 `[video_parse.channel]` 群名单。

`send` 默认只发视频气泡，一份成品一条消息。要群文件的群开成 `file` 或 `both` 也安全：
**气泡在前、文件在后**，两条腿各自兜错——有些群不让普通成员发群文件，发文件那条腿会
失败（实现端还会为一条上传失败的富媒体就地重试到超预算，默认 2 次 / 45 秒），那时只是
少一个文件，既不补一条错，也不影响已经发出去的气泡。只配一条腿时，它自己的失败照旧
往上报，群里能看到「没取到」。

群名单走的是一般的黑白名单：`black` 里的群一律不解析，`white` 非空时只解析名单内
的群。线上 818965288 与 924989840 在 `black` 里——那两个群已经有别的解析机器人。
被名单拦下的链接连截图都不进（`webshot` 本来就把视频站链接让给本插件），所以那两个
群里我们一句话都不说。

## 验证

```sh
cargo test --bin ayjx                                       # 分流、卡片、状态与去重
cargo test --bin ayjx live_reads_the_metadata -- --ignored --nocapture
AYJX_VIDEO_PARSE_LIVE_GROUP=280183116 \
  cargo test --bin ayjx live_takes_ -- --ignored --nocapture
```

后两条会真的往沙盒群发一条视频（气泡 + 群文件）与触发那条链接，跑完自己撤回。
要确认「发出去了没有」看实现端的 `message.list` / `message.get`，不要看 ayjx 的日志。
`[Chat] 发送 ->` 只说明打算发。两条都验成品引用了用户那条链接。

## 加站点

目前只做了 B 站。要加一个站点：在 `is_video_link` 里认它的链接（短链可以先承认、
再像 B 站那样跟随一次跳转），再补一份「拉信息 + 取流」的实现。取片那条路只要求
最后拿到一组可直下的分片地址与它们的字节数，别处不用改。
