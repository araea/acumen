# 文案规范（Content Design · Voice & Tone）

这份文档管机器人在群里说出口的每一句话，以及每一张卡片图上的字。

它是整套设计规范的第三份：入口与十条硬条目见 [`docs/GUIDELINES.md`](GUIDELINES.md)，
交互与行为规范见 [`docs/INTERACTION.md`](INTERACTION.md)。

它与 `res/cards/m3e.css` 分工：那边定「看起来是什么样」，这边定「听起来是什么样」。两者共用同一个前提：用户在群里看到的是一台机器，不是一个人。所以不装人、不卖萌、不渲染情绪，只把事说清楚。

**这份文档不管搭话人格**（`res/ambient/persona.md` + `res/ambient/voice.md`）。
搭话是有意设计成「群里一个普通成员」的，口语、随手打标点、爱接梗。
这里的规则只约束**系统面**：指令回执、卡片、帮助、报错、空态、推送。

---

## 一、声音（Voice）

三句话，任何场景都不变。

**准确。** 说的是事实，有数字就给数字，没有就说没有，不猜、不夸大。写 `✅ 已提取 3 / 5 条`，不写 `✅ 提取完成，收获满满`。

**克制。** 只说不说就会造成误解的话，不评价自己的输出，不替用户判断「这很有用」，不加语气词与感叹号。写 `⏳ 正在生成词云…`，不写 `⏳ 稍等片刻，马上就好啦！`；写 `⚠️ 这条稿件看不了（可能仅限特定地区或需要登录）`，不写 `⚠️ 很遗憾，这条稿件无法播放`。

**直接。** 对「你」说话，先说结果，再说怎么办，出路给到能照做的粒度。写 `❌ 请引用一条包含图片或视频的消息后再发送`，不写 `❌ 未检测到媒体文件，建议您检查一下发送方式是否正确`。

## 二、语气（Tone）

声音不变，语气随场景换。同一件事在六个场景里怎么说见下表。写新文案时先归到其中一类，再照着写。

| 场景 | 语气 | 句首图标 | 结构 |
| --- | --- | --- | --- |
| 成功 | 就事论事，不用形容词 | ✅ | 动作 + 结果（带数字） |
| 进行中 | 说清在等什么，不承诺时长 | ⏳ | 正在 + 做什么 |
| 失败 | 不道歉、不甩锅，说清卡在哪 | ❌ | 现象 + 出路 |
| 空态 | 平静，空不是错 | 📭 | 为什么空 + 怎么让它不空 |
| 引导 | 一个动作，一条能抄的命令 | 💡 | 做什么 + 怎么打 |
| 部分成功 | 说清哪部分成了、哪部分没成 | ⚠️ | 成了什么 + 没成什么 + 要不要重试 |

失败的三种出路，按原因选一种写，不要三种混着写：

- 用户输入问题 → 直接给正确写法（`❌ 请指定索引：智能体/索引`）
- 外部条件问题 → 说清是什么条件，让人能等或能改配置（`被 B 站限流了，过一会儿再试`）
- 机器人自己的问题 → 如实说，并说明替代方案（`出图失败，先给你一份文字版`）

## 三、写法规则（可逐条核对）

### 3.1 人称与语气

用「你」，不用「您」。不写「请」字开头的一段话，「请」只用在必须强调这是一次请求的引导里，一条消息里至多一次。不用「吧」「哦」「啦」「呢」这类语气词，不用波浪线 `~`，不用感叹号 `！`。不评价自己的输出：「方便」「强大」「智能」「一键」这类词一个都不用。

### 3.2 标点

一行以内的提示（状态、错误、空态、引导）句末不加标点（`❌ API 未配置`、`❌ 索引无效`），句内正常用「，」。成段的文字（卡片正文、强调块、文字版报告、推送引言）标点正常用，末句加句号。省略号一律用「…」，不用 `...` 或 `。。。`。并列用「、」，不用「/」，除非是在写两条可选命令（`on/off`）。
括号用全角「（）」，只有在写标识符、路径、命令时用半角 `()`。数字与单位之间不加空格（`3 条`、`2 秒`），数字与中文之间留一个空格（`共 24 条`、`3 个信源`）。冒号用全角「：」，后面不跟空格。

指令本体是唯一的例外，那里的数字紧贴中文（`近7天`、`近30天`、`裁剪 3x3`），因为用户要整条照打，空格打不出来。写进正文引用时仍按上面的规则留空格。

### 3.3 句子

一条消息至多三句，超过三句就是在写文档，搬进卡片或帮助页。先给结果，再给原因：写 `❌ 请指定索引：智能体/索引`，不写「索引参数没有提供，所以无法继续」。

数字写阿拉伯数字（`3`、`120`、`1.5 MB`），不写汉字数字，千分位只在四位以上用。时间用 24 小时制 `HH:MM`，日期用 `YYYY-MM-DD`，时长用「秒 / 分钟 / 小时」。

不写「系统」「程序」「后台」这种以机器为主语的句子：写 `❌ 图片下载失败`，不写 `❌ 系统检测到图片下载异常`。

### 3.4 指令的写法

一律叫「指令」，不叫「命令」「cmd」。写出来的指令要能整条抄走，带上当前前缀。参数占位必填用尖括号 `<插件名>`，可选用方括号 `[路径]`，写进正文时用 `代码格式`。一条引导里只给一条指令，其余放到帮助页，用 `详见 /help` 收尾。

### 3.5 图标

全站只允许六个，且**一条消息至多一个，只能出现在开头**。其余一律用文字。

| 图标 | 含义 | 例子 |
| --- | --- | --- |
| ✅ | 成功、已完成并生效 | `✅ 已提取 3 / 5 条`、`✅ 已清空 2 个智能体的所有历史` |
| ⚠️ | **做成了，但要打折着看**：只做成一部分，或结果带代价 | `⚠️ 切片数量过多，仅发送前 99 张` |
| ❌ | 没做成：这次输入不被接受，或外部条件不允许 | `❌ 索引无效`、`❌ 未检测到媒体文件` |
| ⏳ | 正在进行 | `⏳ 正在生成词云…` |
| 📭 | 空。没有内容，但不是错误 | `📭 历史为空` |
| 💡 | 提示与用法 | `💡 看全部指令：/help` |

**一个符号只表示一种状态。** 拿不准时问一句：**这条消息说的事，成了没有？**
全成了用 ✅，**成了一半、或成了但有代价**用 ⚠️，没成用 ❌。
不成立的三种写法：

| 现在常写成 | 为什么不对 | 改用 |
| --- | --- | --- |
| `⚠️ 未检测到媒体文件` | 用户什么都没做成，这是这次输入不被接受 | ❌ |
| `⚠️ 重启指令未开放` | 同上，指令被拒 | ❌ |
| `⚠️ 已清空 3 个智能体的历史` | 全做成了，没有折扣可打 | ✅ |

⚠️ 是全站**最少**用到的那个符号。它一旦变多，说明有人在拿它当「有情况」用。

**这套符号与 koishi 工作区（[koishi-plugin-guidelines](https://github.com/araea/koishi-plugin-guidelines)）
不是同一套，差异是有意的，不要拿那边的表来对齐。** 那边是
✅ ⏳ 💡 ⚠️ ❌ 📋 🏆：`📋` 承担「罗列」，`🏆` 承担「庆祝」。
这里 `📋` 没有对应物。需要罗列的内容（帮助、清单、排行榜）一律出卡片图，
不用符号在正文里做目录。「庆祝」在 ayjx 属于搭话人格，不在本规范的管辖内。
空状态这边用 `📭`，表达「没有内容，但不是错误」。

- **卡片图内不用图标。** 卡片有自己的视觉语言（徽章、色块、层级），图标会与
  它冲突。卡片要表达状态就画徽章，不要写 ✅。
- 不用表情符号代替标点，不用 🎉✨🔥 这类装饰性表情。
- 文本回复里另有一类**行内记号**，它们承担排版功能，不算状态图标：

  | 记号 | 用途 | 例 |
  | --- | --- | --- |
  | `▍` | 分区名 | `▍消息 · 媒体（3 项）` |
  | `🔗` | 链接行 | `   🔗 原文：https://…` |
  | `📄` | 原文行 | `   📄 原文：https://…` |

  这一类只出现在**纯文本的行首**，用于让眼睛快速分辨「这一行是什么」。
  状态图标（那六个）出现在消息开头。两者不要混用：`✅ 🔗 …` 是错的。
  注意 `🔗` / `📄` 还是资讯提取的**解析标记**（`parse_entry_links` 按前缀反解
  旧记录），改它们要同时改解析。

- **送进模型的提示词里的分段标记不算文案。** `persona.rs` 的 `【对象】`「【统计】」
  「【发言样本】」、`oai/utils.rs` 的 `【#1 用户 | 时间】` 是给模型看的标记，
  不是群里说出口的话。它们的读者是模型，`【】` 在那里比「」更不容易和正文混淆。
  这份文档管的是「机器人在群里说出口的每一句话」，提示词不在其内。

### 3.6 状态词

状态词必须能**互换着读**：同一种状态在群里、在卡片上、在配置清单里都得是
同一个词。只有「格子里」允许用短写。

| 状态 | 用 | 不用 |
| --- | --- | --- |
| 插件开关（句子里） | 已启用 / 已停用 | 已开启、已关闭、已禁用、打开、关闭 |
| 插件开关（状态清单的一格） | 开 / 关 | 启用、停用（格子里太长） |
| 生命周期未跑完 | 待重启 | 待生效、需重启、待初始化 |
| 推送目标 | 已开启推送 / 未开启推送 | 已启用推送 |
| 联网搜索的房间级开关 | 已打开 / 已关闭，后面括注是谁定的（`（本房间设置）`／`（跟随全局）`） | 只写「跟随全局」（看不出当下开没开） |
| 历史记录 | 公有 / 私有 | 公开 / 私人 |

同一个句子里不要出现两组状态词（`✅ 已启用推送，插件已开启`）。

### 3.6.1 空不是故障

「这段时间没有数据」和「生成失败」是两件事，**不能用同一个图标**。
前者用 📭，后者用 ❌。把它写成 `❌ 生成失败：暂无数据` 有两个错：
它把空态说成了故障，又让用户去找一个并不存在的毛病。

已经这么改的两处（`stats` 与 `wordcloud`）走同一条路：底层把「没数据」与「真失败」
分成两个返回值，上层分别渲染：

```text
📭 本群今日发言排行榜没有数据
换一个时间范围，或先让群里聊几句
```

**推送侧的日志也要分开**：冷群没数据是常态，用 `info!` 记一句就够。
只在真失败时用 `warn!`。混在一个级别里，日志就指不出哪次是真的坏了。

### 3.7 术语表

| 用 | 不用 | 备注 |
| --- | --- | --- |
| 插件 | 模块、扩展、功能 | |
| 指令 | 命令、cmd | |
| 群 / 私聊 | 群聊、私信、频道 | 作通道名时统一这两个词 |
| 引用 | 回复引用、quote | 「引用某条消息后发送」 |
| 配置键 | 字段、参数名、选项 | |
| 房间 | 会话、对话、频道 | 指 oai 的房间时 |
| 智能体 | agent、角色、bot | |
| 内置 | pi | 界面上一律叫「内置」，`pi` 只是引擎关键字 |
| 出图 | 渲染、生成图片 | 指卡片截图时 |
| 重启 | 重载、重新启动 | |

未经确认的内部名（配置键、供应商名、模型名）照原样写，不改写、不翻译。那些是用户要去核对的东西，改写了就对不上。

### 3.8 卡片文案的分层

一张卡片上的字分六层，每层只放一类信息。写新卡片时按这个顺序填。

| 层 | 放什么 | 例 |
| --- | --- | --- |
| 眉标 | 这张卡是什么。固定词，不随数据变 | `用户画像 · USER PROFILE` |
| 标题 | 本次的对象 | `插件总览`、`阿甲`、`AIHOT 大模型排行榜` |
| 副标题 | 范围与规模 | `按用途查找功能 · 指令前缀 /`、`共 24 项` |
| 小节 | 分区名 + 英文简写 + 条数 | `指令 · COMMANDS · 9 条` |
| 条目 | 名称 + 键名 + 一句话说明 | `自动重启 / restart / 每日定时重启…` |
| 页脚 | 左：出处与口径；右：下一步动作 | `开关状态以当前配置为准` + `/help <插件名>` |

三条额外的要求：

- **口径句**：凡是汇总出来的数字，卡片上要有一句话说明它怎么来的
  （`观测区间 … · 样本 120 条`、`共识分由多家公开评测榜单统一折算`）。
- **有损声明**：推断出来的东西要说清是推断（画像卡的图例与页脚）。
- **下一步**：每张卡的页脚都给一条能立刻执行的指令，不要让读者看完不知道干什么。

## 四、改文案时的检查清单

写完一段用户可见的文案，逐条过：

- [ ] 归到六类场景里的哪一类，语气对上了吗
- [ ] 一行以内的话句末有没有多余的句号，有没有语气词、波浪线、感叹号、自夸的词
- [ ] 失败与空态给了出路吗，出路是不是能照做的粒度
- [ ] 状态词是从 3.6 那张表里选的吗，句子里有没有混两组
- [ ] 图标是六个之一吗，只有开头一个吗，卡片图里有没有混进图标
- [ ] 术语查过 3.7 那张表吗，有没有把配置键翻译成中文
- [ ] 写出的指令能整条抄走吗，下一步明确给出来了吗

## 五、这条规则该改的时候

改之前先想清楚一件事：**用户会不会因此对不上号**。

- 加一个新状态词 → 先看 3.6 那张表里有没有现成能用的。
- 加一个新图标 → 只有当前六个表达不了才加，且要同时改这张表、改已有文案。
- 改术语 → 全仓一次改完（`rg` 一遍旧词），不能新旧并存。

改动落地时同步三处：这份文档、`res/cards/m3e.css` 里对应的组件文案（如果有）、
以及各插件的文案本身。
